# 乳癌希望之島｜開發規格大綱 v0.1

## 1. 專案定位

### 暫定名稱

**乳癌希望之島**（工作名稱）

### 核心概念

以一座溫暖、可探索的島嶼呈現台大癌醫乳癌照護旅程。台大癌醫 Q 版建築作為中心地標；乳房攝影、乳房超音波、病理、乳房外科、化學治療、手術、放射治療、復健與支持服務等，轉化為島上的照護據點與資訊卡片。

使用者由認識疾病、檢查與診斷，逐步了解治療團隊如何接力照護；另設紀念與支持空間，連結乳癌紀念活動。

### 參考方向

參考「你的肝苦，我們一起扛」特展呈現的三項做法：以易記的情感主題作為入口、以多專科協作作為核心訊息、用病人照護經驗說明治療路徑因人而異。乳癌希望之島將這些做法轉化為空間導覽和互動卡片。

## 2. 專案目標

1. 讓病人與家屬容易理解乳癌的基本知識、風險與就醫流程。
2. 讓使用者看見不同科部、檢查室及照護專業如何共同參與。
3. 為乳癌紀念活動提供可現場操作、可透過 QR code 延伸閱讀的數位體驗。
4. 以尊重、陪伴和希望為情緒基調，避免恐懼式宣傳及把治療描寫成單一路徑。
5. 建立可持續更新的衛教內容與活動架構，供後續年度活動沿用。

## 3. 目標使用者

- 正在接受檢查或治療的乳癌病人
- 病人家屬與照顧者
- 一般民眾與乳癌篩檢宣導活動參與者
- 台大癌醫跨專科醫療團隊及活動現場工作人員

不同使用者可從不同入口進入，不要求使用者先選擇或公開自己的病人身分。

## 4. 核心體驗與導覽路線

### 4.1 認識乳癌

介紹乳癌基本知識、風險概念、可採取的健康行動，以及何時應尋求醫療評估。內容由院內相關專業審閱；網站提供一般衛教，不作個人診斷或治療建議。

### 4.2 走過照護旅程

以流程而非單位名錄帶領使用者探索：

```text
認識與評估 → 影像檢查 → 必要時切片與病理 → 討論治療選項
→ 手術／藥物／放射治療等照護 → 復原、追蹤與支持
```

此為一般性導覽示意。每位病人的實際檢查與治療順序由醫療團隊依個別狀況討論。

### 4.3 紀念與支持

提供活動介紹、團隊影片、病友支持資訊，以及自願參與的祝福或點燈互動。公開留言須採明確同意、匿名選項、審核與撤下流程。

## 5. 島嶼場景與據點清單

### 5.1 中心地標

- 台大癌醫 Q 版建築：全島主要辨識物與返回全景的導覽錨點。
- 希望燈塔／島中央廣場：紀念活動、祝福或集體點燈的中心場景。
- 照護旅程主徑：串接檢查、診斷、治療、復原等不同區域。

### 5.3 六角島嶼分類構想

- 每個主要科部／照護主題配置一座六角形島區，讓分類關係直接反映在地圖空間；中央癌醫地標作為共同核心，外圍以步道或短橋連接各島。
- 六角形是「區域邊界與分類提示」，不要求每個房屋或小物都做成六角形；建築仍使用簡單圓角亭、矩形照護屋等低模母型，避免視覺過度像棋盤。
- 第一版以 6–8 個六角區域為上限。可將相關科部合併為較大的主題島，例如「檢查與診斷」、「手術與重建」、「藥物治療」、「放射治療」、「復原支持」、「紀念與陪伴」。細分單位放入島內據點卡片。
- 每區以低彩度底色、入口地標和圖示共同辨識；顏色不是唯一區分方式，避免色覺差異造成辨識障礙。
- 六角地圖需在手機提供簡化 2D 導覽與科部清單，避免縮小後六角區域及標籤難以點選。

## 6. 功能需求

### 6.1 必要功能（MVP）

- 首頁提供「照護旅程」、「自由探索」、「紀念活動」三個入口；預設引導第一次使用者進入照護旅程。
- 中央地標與 6–8 個六角分類區；桌機／大螢幕顯示全島鳥瞰，手機提供全島地圖和第一人稱漫遊兩種視角。
- 手機漫遊提供虛擬搖桿及點選目的地自動行走；支援切回第三人稱、2D 地圖、文字清單和減少動態模式。
- 可點選的建築／據點與對應資訊卡片。
- 文字清單模式，可搜尋據點、科部與衛教主題。
- 照護旅程導覽，具上一站、下一站、目前進度及跳過功能，可從路線步驟跳轉至相應據點。
- 卡片之間的「相關照護／下一站」連結。
- 以網址參數直接開啟指定據點或卡片，供 QR code 與實體展板使用。
- 本機暫存已造訪據點；不登入、不建立個人醫療檔案，也不把完成度解讀為療程進度。
- 活動介紹、時間地點及講座／影片入口。
- 2D／清單備援：WebGL 無法使用時，所有核心內容仍可操作。
- 桌機、平板與手機版響應式介面。

### 6.2 活動互動功能（第二階段）

- 點亮希望燈或送出祝福；可選擇匿名且不公開。
- 多位訪客在地圖中互相看見彼此的角色位置；須限制更新頻率與同時可見人數。
- 大螢幕即時呈現各島區參與狀態或彙總瀏覽量。
- 可由工作人員啟動預設導覽路線或循環播放模式；如需訪客鏡頭上大螢幕，必須由本人主動分享。

### 6.3 延伸功能（需另行評估）

- 可自訂的 Q 版角色與行程探索。
- 個人化導覽路線。
- 病友故事或影音專區。
- 多語版本。
- 手機陀螺儀、WebXR／AR 等沉浸功能。
- 島民角色造型原型：女性／男性外觀呈現，搭配病友／訪客日常服、醫師白袍、護理師制服、手術室刷手服；共用同一套身體比例與骨架。
- 上傳大頭照的本機預覽原型：照片僅在瀏覽器記憶體中裁切，不上傳、不保存；提供清除按鈕，關閉頁面即清除。此功能目前只做 2D 頭像貼合示意，不代表 AI 生成完整 3D 角色。

若未來改為雲端照片處理或需保存角色，須另行取得明確同意、定義保存期限與刪除流程，並先完成院方個資及資安評估。角色可匿名使用，也可完全跳過照片上傳。

## 7. 資訊卡片內容模板

每張據點卡片建議採一致欄位：

1. 這個地方／團隊的角色
2. 病人通常在什麼情境接觸到這項服務
3. 服務流程或檢查／治療的基本說明
4. 常見問題與可準備事項
5. 相關科部或照護團隊
6. 上一站／下一站／相關主題
7. 院內正式資訊連結及聯絡方式（經確認後提供）
8. 內容負責單位、審閱者與更新日期

## 8. 視覺與互動設計方向

### 8.1 主視覺風格

- 整體語氣：親切、安定、有陪伴感；採原創 Q 版生活模擬風格，不臨摹特定遊戲角色、建築或介面。
- 人物比例：1.5–2 頭身，大頭、短身、輪廓清楚；人物應比一般建築比例更大，是情緒與照護關係的主角。
- 建築比例：一般照護據點約為 2–3 個人物高度；癌醫主建築約為 6–8 個人物高度。追求「意象可辨識」，不追求真實尺度。
- 台大癌醫地標：保留弧形深色玻璃量體、兩側暖灰米色翼樓及入口雨棚等核心辨識特徵，其餘細節簡化。
- 畫面密度：保留明顯留白與寬路徑；單一畫面同時強調的據點不超過 3 個，避免樹木、花卉和裝飾物彼此競爭。
- 材質與光線：霧面、少紋理、柔和烘焙陰影；避免寫實反射、複雜玻璃、景深特效及高成本即時光影。

### 8.2 莫蘭迪低彩度色票（工作版）

| 用途 | 色彩 | HEX | 使用原則 |
|---|---|---|---|
| 主背景／卡片 | 暖米白 | `#E8E1D7` | 大面積底色，降低醫療空間壓力感 |
| 路徑／建築基底 | 沙岩米 | `#C8B9A8` | 道路、翼樓和中性表面 |
| 植被 | 鼠尾草綠 | `#9AA58F` | 草地、樹冠；避免鮮綠 |
| 導覽／資訊 | 灰霧藍 | `#8296A1` | 次要按鈕、資訊節點和選取提示 |
| 活動識別 | 灰粉玫瑰 | `#B98F91` | 少量重點、希望活動與主要按鈕 |
| 文字／深色量體 | 灰藍炭 | `#55656B` | 正文、外框及癌醫玻璃意象 |
| 輔助中性色 | 暖灰褐 | `#8F857D` | 次要文字、岩岸和陰影 |

粉色只作活動識別和操作重點，不將整座島染成粉紅色。最終介面色票須經 WCAG 對比測試；若低彩度色不適合作文字，改以深色文字搭配低彩度底色，而非提高飽和度。

### 8.3 低模與模組化建模規則

- 癌醫主建築由約 5 個主要量體加 1 個入口雨棚組成；只保留最具辨識度的弧形塔樓、翼樓與入口關係。
- 每個照護據點以 2–3 個大形體完成，優先由「圓角診療亭」、「矩形照護小屋」、「中央地標」三種母型變化。
- 單一資產原則上不超過 3 種主要材質；門窗、屋頂、招牌底座及燈具共用材質圖集。
- 門窗、樹、長椅、路燈、指標和路徑採共用模組；以色彩、圖示和少量輪廓差異辨識科部。
- 不製作單朵小花、室內陳設、密集屋頂設備、細欄杆、複雜道路標線或逐扇窗戶的內容。
- 植物以少量大樹冠和灌木團塊呈現；水面使用單純色塊及低頻率動畫。
- 第一輪行動裝置效能目標：全景可見幾何約 25 萬三角形以內、同時繪製呼叫約 100 次以內；正式數值須以目標手機實測調整。
- 主要地標、據點與人物至少提供 2–3 級 LOD；遠景以低模或替代圖示呈現。

### 8.4 互動模式

| 模式 | 使用情境 | 核心互動 | 結束狀態 |
|---|---|---|---|
| 照護旅程 | 第一次使用、需要明確方向 | 依序前往據點、閱讀 20 秒摘要，可展開詳細內容 | 顯示已認識的主題與相關資源，不評分 |
| 自由探索 | 想找特定檢查、科部或問題 | 點選地圖、搜尋或清單；鏡頭移至據點並開啟卡片 | 可返回全景或前往相關照護 |
| 紀念活動 | 現場活動、支持與倡議 | 活動介紹、點燈或祝福、團隊影片 | 提供院內正式資源與離開頁面 |

### 8.5 據點操作與資訊分層

1. 使用者點選據點、清單項目或掃描 QR code。
2. 鏡頭以 0.6–1.0 秒平移至目標；啟用「減少動態」時直接切換，不播放飛行動畫。
3. 手機開啟底部抽屜，桌機開啟側邊卡片；場景仍可看見目前位置。
4. 第一層為約 20 秒可讀完的摘要：一句話角色說明、三個重點、主要行動。
5. 第二層為 1–2 分鐘內容：流程、準備事項、常見問題和相關團隊。
6. 第三層連結院內正式網頁、影片、聯絡方式或下載資料。
7. 使用者可選擇上一站、下一站、相關主題、返回全景或改用文字清單。

卡片固定保留關閉、返回全景、目前位置及文字清單入口。建築標籤只顯示名稱或短標題，詳細醫療資訊不得只放在 3D 場景或圖像內。

### 8.6 回饋、動畫與防迷路規則

- 點選前以柔和外框或底座提示可互動物件；不使用持續閃爍。
- 選取後只突出一個主要據點，其他據點降低明度但保持可辨識。
- 導覽路線顯示目前站、已看過與下一站；已造訪狀態僅儲存在使用者裝置。
- 環境動畫以緩慢水面、樹葉擺動和燈光呼吸為限；角色不需複雜走路或即時群聚模擬。
- 若 8 秒內未完成 3D 載入，先呈現文字清單與卡片入口，讓內容不受場景阻擋。
- 所有模式皆提供鍵盤、螢幕閱讀器、大字體、減少動態和 2D 清單備援。

### 8.7 第一版刻意不做

- 不做帳號登入、病歷串接或依個人診斷推薦治療。
- 不做即時多人、開放聊天室、未審核公開留言或複雜角色捏臉。
- 不把「造訪完成度」做成醫療任務、競賽分數或治療成就。
- 不以寫實疼痛、手術畫面或恐懼式動畫吸引注意。

### 8.8 六角島地圖與人物漫遊

- 島嶼採「中心地標＋環狀六角區＋外圍海岸」的概念佈局；每個六角區代表一組照護分類，步道在區域交界處自然銜接。
- 島民可沿步道自由移動。第一版以預先設計的步道網格、碰撞邊界和簡單路徑尋路實作，不讓人物穿越建築、海岸或展區邊界。
- 手機提供第一人稱視角作為漫遊選項：虛擬搖桿或點地移動、拖曳調整視角、點選地標開卡片；地圖／指南按鈕可隨時定位、切換第三人稱或回到清單。
- 初次進入可先選擇代表角色外觀（例如不同服裝色或配件），不輸入姓名、不要求建立帳號；角色只代表當次匿名訪客。
- 第一人稱移動提供簡易模式：點選目的地後自動沿路前往。另提供靜態 2D 地圖、第三人稱跟隨和減少動態模式，照顧不習慣搖桿或容易暈動的使用者。
- 遠景島民可使用簡化動畫或低成本預設路徑；初版不做大量真人即時連線、語音聊天或角色碰撞互動。

### 8.9 大螢幕與手機雙視角活動流程

| 螢幕 | 顯示內容 | 使用者操作 |
|---|---|---|
| 活動大螢幕 | 全島鳥瞰、六角區分類、目前活動主題與 QR code；主持人可切換導覽焦點 | 主持人或工作人員控制全島視角、切換導覽路線及重設活動狀態 |
| 參與者手機 | 同一座島的第一人稱或第三人稱個人視角、移動控制、據點卡片、返回地圖入口 | 掃 QR code 後選擇角色、自由探索或跟隨導覽、閱讀衛教卡片 |

建議流程：大螢幕呈現島嶼與 QR code → 參與者掃碼進入活動場次 → 選擇匿名島民外觀 → 手機直接出生在迎賓廣場 → 自由漫遊或跟隨「認識照護旅程」 → 點選六角區據點閱讀衛教 → 返回中央廣場參與紀念活動。QR code 可印在實體展板上，直接開啟相應島區。

大螢幕預設保持穩定的全島鳥瞰，避免所有人的鏡頭互相搶控制權。主持人可選擇「帶大家看某一區」模式，將全場共同聚焦於一個據點。若未來需要即時呈現參與人數或跟隨單一訪客，列為第二階段；訪客位置上大螢幕前須由本人主動同意，並設自動結束時間。

QR 連結只建立短效匿名活動工作階段，不要求登入、不綁定病人身分、不記錄個人病史。活動結束後清除工作階段識別碼；若保留統計，僅保留總參與人次、各區瀏覽量等去識別化彙總資料。

### 8.10 同步與技術分層（概念）

- 3D 地圖和互動內容由手機網頁載入；初版定位為手機瀏覽器 WebGL 體驗，不把安裝 App 或 AR 眼鏡作為進場條件。
- 每位島民的角色位置由本人手機端本機運算；第一版不需位置同步伺服器。
- 大螢幕的主持人視角由活動控制端管理；參與者手機操作不會直接改變大螢幕鏡頭。
- 第二階段若需各區參與人次，可收集短效匿名工作階段的區域事件並只呈現彙總值；若需看到其他島民，可採低頻率位置同步，只顯示簡化小角色並限制同時可見數，先評估現場 Wi-Fi、併發量和個資風險。
- 資產採分區延遲載入：先下載迎賓廣場與低模地圖，再載入使用者接近的六角區；卡片文字優先於 3D 貼圖載入。
- 網路或 WebGL 不穩時，使用者仍可切換 2D 六角地圖、清單及純文字卡片；活動大螢幕可播放預錄全景或簡報版路線。

## 9. 技術與資料規格

### 9.1 前端架構（選型結論）

- 技術選型定為 TypeScript、Vite、React、Three.js 與 React Three Fiber。Three.js 負責 3D 場景與 WebGL 2 渲染；React 負責導覽、搜尋、資訊卡、活動資訊與無障礙介面。
- 第一版使用 Three.js `WebGLRenderer`，以 WebGL 2 為正式支援基線。WebGPU 僅作實驗分支，不列入活動上線必要條件。
- 使用 Vite 建置單頁網站；同一份前端程式依路由提供 `/visit` 參與者手機、`/display` 活動大螢幕及 `/control` 主持人控制台。
- 場景物件與衛教內容以穩定 ID 關聯，避免內容與模型寫死在同一段程式碼。
- 3D 場景、卡片內容、旅程路線及活動模組分開維護。
- 第一版不使用 Next.js 伺服器端渲染。主要體驗必須在瀏覽器載入後運作，採靜態建置可減少部署元件與活動現場故障點。

### 9.2 建議資料實體

- `place`：據點 ID、名稱、類型、模型／座標、關聯卡片。
- `content_card`：標題、摘要、正文、FAQ、媒體、聯絡資訊、審閱與更新資訊。
- `care_path`：路線名稱、適用入口、步驟順序及每步關聯據點。
- `relation`：相關政策／服務節點、關係說明、證據來源。
- `event`：活動時間、場地、議程、影片、QR code 目標。
- `message`（如啟用留言）：內容、匿名狀態、公開同意、審核狀態、撤下時間。
- `content_revision`：據點 ID、修改者角色、版本、醫療審閱者、審閱日期、發布狀態與變更紀錄。

### 9.3 部署方向

- 開發與院內展示階段使用 Netlify 連接 Git repository，提供自動建置與 Deploy Preview；Netlify 僅作開發預覽及設計討論，不列為正式服務依賴。
- 正式版交付可攜式 Docker Compose 套件，部署在院方 Linux VM／伺服器；最小型態用 Nginx 提供靜態網站和 3D 資產，無需 GPU、Node.js 常駐服務或外部 CDN。
- 院方若允許公開流量走 Cloudflare CDN，可將正式版設為院內 origin 加 Cloudflare 快取；若要求全院內網運作，就由院內 DNS／反向代理和訪客 Wi-Fi 提供存取。
- 衛教內容以版本控管的 JSON／Markdown 儲存，經 CMS 審核發布後重新建置靜態網站；不讓公開活動頁直接依賴後台資料庫。
- 場景模型、貼圖與影音採壓縮及延遲載入；首屏先呈現基本介面與文字入口。
- 每次更新需同步檢查模型資產、資料 ID、卡片及路線連結。
- 活動現場保留本機靜態備份、離線影片、靜態展板或 2D 網頁備援。

正式網域、內外網可達範圍、反向代理、TLS 憑證、院內 VM 規格與維運責任由資訊室確認。若掃 QR code 的手機要使用行動網路而不是院方訪客 Wi-Fi，內部主機必須透過院方核准的公開入口／DMZ 反向代理供 HTTPS 存取。

### 9.3.1 科部內容維護後台

- 建議設置簡單的院內內容後台，科部可維護自己負責的據點卡片、FAQ、正式連結、圖片替代文字與內容更新日期。
- 採三種角色：科部編輯者建立草稿；專科／活動內容審閱者核對醫療資訊；中央發布者核准後發布。每次發布保留版本、作者、審閱者及日期，可回復前版。
- 後台欄位採結構化表單，不要求同仁編輯 JSON 或 3D 場景；所有圖文內容仍遵循統一模板與字數限制。
- 公開端只讀取已核准版本。發布時將內容編譯成靜態 JSON／HTML 並部署至 CDN，活動期間不讓公開頁面依賴 CMS 資料庫即時查詢。
- 若院內已有支援分科權限、審核流程和版本紀錄的 CMS，優先沿用；否則建置小型院內後台。避免各科部直接編輯公開網站或 3D 場景檔。
- 初期可由中央管理員協助各科上稿，但須保留「科部負責人、醫療審閱者、下次檢視日期」欄位，確保內容責任清楚。

### 9.4 3D 資產與執行架構

- Blender 為主要建模工具；交付格式統一為 glTF／GLB，不把 Blender 原始檔直接交給網站載入。
- 網格使用 Meshopt 或 Draco 壓縮，貼圖使用 KTX2／Basis Universal；材質以低彩度 PBR 基本材質為主，避免即時反射、透明玻璃和多層後製。
- 場景拆成「共用核心、中央廣場、六角島區、角色」四類資產。使用者先載入核心與出生區，再依接近區域延遲載入其他島區。
- 人物移動第一版採步道導航網格或節點路線加簡單碰撞體；不需要完整物理模擬。自動行走與 NPC 漫遊共用同一套路徑資料。
- 大螢幕與手機共用場景資料、模型和內容 ID，但使用不同攝影機、畫質層級及操作介面。

### 9.4.1 可重複使用的元件製作流程

所有 3D 與介面資產採元件化製作，以穩定 ID 連結模型、程式互動及內容資料；更換外觀或模型時，不改動據點 ID 和衛教卡片 ID。

- ID 類型：`CHR` 角色、`BLD` 建築、`ENV` 地形／六角區、`PROP` 場景道具、`UI` 介面元件；後接用途與三位序號，例如 `CHR-VISITOR-001`、`BLD-MAMMO-001`。
- 固定製作關卡：需求 brief → 多角度概念圖 → Blender 灰模 → 低模／材質 → GLB 與 metadata 匯出 → 單島測試場景 → 審核發布。概念圖未確認前不做細模，GLB 未通過測試場景前不進正式網站。
- 角色視圖固定含正面、左右側面、背面、左右斜前，採中性 A-pose；建築含正面、左右側、背面、俯視與 3/4 視角；地形需標示拼接邊界、俯視與高度；道具需標示擺放錨點與碰撞盒。
- 所有資產附 `component.yaml`：穩定 ID、版本、用途、比例／單位、原點、面向、LOD／面數預算、互動 ID、碰撞體、動畫名、概念圖、原始檔、GLB、審閱者與狀態。
- 每個元件封裝為獨立資料夾：`assets/<ID>/component.yaml`、`reference/`、`source/`、`export/`。版本改動保留舊版與變更原因，網站程式只依 ID 載入元件。
- 共用同一套莫蘭迪色票與低模規則：霧面、大形體、每資產最多 3 種主要材質；避免高飽和、細碎貼圖與無法在手機辨識的小配件。角色基準高度正規化為 1.0；建築以角色高度倍數記錄，維持人物較大的比例。
- 發布關卡檢查造型一致、匯入方向與尺寸正確、材質和貼圖無遺失、碰撞與互動正確、LOD 不跳位、手機與大螢幕辨識度足夠，並記錄 GLB 大小、三角形、材質數、貼圖大小及 draw calls。
- 醫療衛教文字與模型分開管理；如模型或圖示承載醫療含義，由對應科部審閱。角色及場景不表達診斷、療效或病人個人狀態。

第一個資產樣板為 `CHR-VISITOR-001` 島民訪客角色，角色設定圖採六角度一致比例；後續角色使用共用骨架及服裝變體。建模與匯出規則詳見「元件製作與重複使用流程 v0.1」。

### 9.4.2 角色、頭像與醫院建築元件族

- 角色共用一套基礎身體比例和骨架，外觀呈現與服裝以變體組合：病友／訪客日常服、醫師白袍、護理師制服、手術室刷手服。男女版本共用相同動畫命名和碰撞規則；個別服裝進入正式建模前需補多角度設定圖。
- 頭像照片原型採瀏覽器本機處理，只把選取照片裁切至角色頭部預覽，不使用伺服器、不寫入資料庫或本機儲存空間。正式 3D 角色若採照片貼圖，必須保留跳過、預覽、清除和離島後清除；雲端 AI 生成另需院方審查與明確同意。
- 中心地標建築 ID 為 `BLD-NTUCC-001`，參考院方提供的空拍與外觀影像，保留中央弧形深色玻璃塔、低樓翼樓和入口雨棚，移除逐扇窗戶、屋頂設備等細節。模型公開使用前由院方確認外觀與素材使用範圍。
- 科室採 `BLD-DEPARTMENT-001` 共用小屋母型，以入口圖示與資料欄位辨識科室，不為每科重新建一套房屋；第一批包含乳房攝影、乳房超音波、病理、化學治療、手術室及放射治療。
- 科室名稱和醫療資訊以網頁文字覆蓋圖示，不能只烘焙在模型貼圖中；各據點仍以穩定 `place_id` 關聯獨立內容卡片。
- 角色、主建築、科室母型各自保有獨立來源檔、GLB、metadata、預覽圖和版本；網站只依穩定 ID 載入，外觀更新不改動衛教內容 ID。

### 9.5 前端效能預算

| 項目 | 手機目標 | 大螢幕目標 |
|---|---:|---:|
| 最低畫面更新率 | 穩定 30 FPS | 1080p 穩定 30–60 FPS |
| 裝置像素比 | 上限 1.25–1.5 | 依顯示設備設定，上限 2 |
| 同畫面三角形 | 約 20–25 萬以內 | 約 50–80 萬以內 |
| Draw calls | 約 80–100 以內 | 約 150 以內 |
| 首次可操作下載量 | 8–12 MB 以內 | 15–25 MB 以內 |
| 全部 3D 資產 | 30 MB 以內為目標 | 可載入較高畫質資產 |

以上數值是開發預算，最終驗收仍以實機量測為準。應在 iPhone Safari、Android Chrome 和活動大螢幕電腦建立固定效能測試場景；偵測到低效能時自動降低像素比、陰影、植栽數與可見島民數量。

### 9.6 後端與即時同步分期

#### 第一版

- 網站、模型與衛教卡片由 CDN 提供；所有 3D 渲染在手機或大螢幕本機執行，伺服器不渲染畫面，因此不需要伺服器 GPU。
- QR code 可直接包含活動代碼與出生島區。若只需各自漫遊，不必維持 WebSocket，也不需要常駐應用伺服器。
- 如需匿名活動人次、島區瀏覽量和主持人焦點，可用輕量 API 接收事件；只保存彙總資料。

#### 第二階段即時島民

- 若參與者需要互相看到角色，加入 WebSocket 場次服務。雲端部署可使用 Cloudflare Workers 與 Durable Objects；院內部署則使用 Node.js 或 Go WebSocket 服務。
- 手機只上傳角色 ID、島區、位置、方向和動畫狀態；建議每秒同步 2–5 次，由客戶端插值顯示，不傳送影像或語音。
- 大螢幕只顯示經抽樣或分群的島民，設定同時可見上限，避免參與人數增加時拖慢瀏覽器。

### 9.7 部署硬體與現場設備

| 用途 | 建議最低配置 | 說明 |
|---|---|---|
| 靜態網站／第一版 | 不需自有伺服器 | 使用 CDN 靜態託管；每台終端電腦自行渲染自己的螢幕 |
| 院內正式靜態網站 VM | 2 vCPU、4 GB RAM、20 GB SSD 起始 | Docker Compose＋Nginx 提供前端、模型與 2D 備援；無需 GPU |
| CMS 及審核後台 | 起始 2–4 vCPU、8 GB RAM、40–80 GB SSD | 只供院內編輯與發布；無需 GPU。可沿用院內既有 VM 平台 |
| 即時同步 VM（第二階段） | 4 vCPU、8 GB RAM、40 GB SSD 起始 | 低頻率 WebSocket 位置同步估算；活動前須按實際併發壓力測試 |
| 每台 1080p 顯示端 | 4 核心以上 CPU、8 GB RAM、支援 WebGL 2 的整合 GPU、SSD | 每台電腦連一台螢幕並載入自己的顯示路由；重複使用資產快取 |
| 4K 主螢幕顯示端 | 6 核心以上或 Apple silicon、16 GB RAM、支援 4K60 輸出的現代整合 GPU | 先以 1440p 3D 場景加原生解析度文字 UI 測試；只有需要原生 4K 3D、複雜陰影或大量動畫時才加獨立 GPU |
| 建模工作站 | 32 GB RAM、8 GB 以上獨立顯示記憶體較佳 | 用於 Blender 建模、貼圖烘焙及資產壓縮；不需使用 DGX |

現場網路負載主要發生在掃碼後的首次資產下載。若 100 人同時載入 10 MB，總流量約 1 GB；應將首包控制在 8–12 MB，院外公開時用 CDN 快取，院內活動時在本機網路快取，並於活動前實測 Wi-Fi 和有線網路。建議準備 Wi-Fi 6 等級基地台與至少 300 Mbps 對外頻寬；若參與者集中在同一時間掃碼，500 Mbps 較有餘裕。大螢幕顯示端可走有線網路，活動控制端與各螢幕以場次代碼同步焦點；如不要求即時同步，各螢幕可獨立播放不同島區內容。

多螢幕架構採「一台小電腦驅動一台螢幕」：4K 主螢幕顯示全島，其他螢幕可顯示特定六角區、衛教卡片或活動照片。所有顯示端都從同一網站載入共用資產，但各自使用適合解析度的畫質設定。建議先以現有小電腦做 1080p／4K 原型測試，再依測試結果決定是否添購獨立 GPU。

NVIDIA DGX Spark 的 HDMI 2.1a 支援 4K 顯示，可直接驅動一台 4K 螢幕；若用於本專案，它是顯示端電腦之一，不代表其他螢幕需要連接它，也不需要讓它替手機伺服器端渲染。若 DGX Spark 還要承擔 AI 推論或研究運算，建議仍讓它專職運算，4K 顯示改由較小型電腦負責。citeturn10search0turn10search1

- 希望之島需另有院內內容審核流程與穩定執行中的互動網站；造島工坊所述的 AI 生成更新方式本身不等於多科部協作 CMS。
- 該網站授權聲明限制修改、轉傳與商業使用，且限定其課程學員使用；本案僅參考其工作流程概念，不直接複製程式碼、素材或造島包。
- 參考來源：[造島工坊｜3D 島嶼網站生成器](https://isleforge-tw.netlify.app/)。

### 9.10 開發預覽與院內正式交付

- 開發者推送 Git 分支後，Netlify 建置 Vite 的 `dist/` 並提供預覽網址，供醫療內容、視覺和互動審查；預覽環境使用合成示例內容，不放病友資料。
- 正式交付包含原始碼、GLB／KTX2 模型資產、已建置網站、`Dockerfile`、`compose.yaml`、Nginx 設定、環境變數範例、安裝／更新／回復指引及 SHA256 檔案清單。
- Nginx 容器只負責傳送靜態檔案；容器不需要 GPU。若第一版不啟用 CMS 或即時同步，正式部署只需一個 Web 容器，設定持久化的部署備份即可。
- 若啟用 CMS，另以獨立服務和資料庫保存草稿、審核紀錄及發布版本；CMS 管理介面限院內網或院方 SSO／Access 保護。公開網站只收到已核准內容的發布檔。
- 院方可選擇在院內 VM 使用 `docker compose up -d` 部署；正式更新以固定版本映像或版本化部署包執行，保留上一版以便回復。
- Netlify Deploy Preview 適合評審和跨部門確認，正式版由院方主機提供服務；Netlify 本身不作正式版資料或應用伺服器。

### 9.8 框架選型結論

| 選項 | 判斷 |
|---|---|
| Three.js＋React Three Fiber | 採用。適合以網頁 UI、衛教卡片和客製 3D 場景整合，能以靜態網站部署 |
| 原生 Three.js | 保留作底層能力；整個專案直接使用會增加狀態與介面整合成本 |
| Babylon.js | 內建攝影機、碰撞、導航與 XR 較完整；若第一人稱遊戲功能成為主體可重新評估 |
| Unity WebGL | 初始下載與記憶體成本較高，不適合作為掃 QR code 即開即用的第一版 |
| WebGPU | 暫不作第一版基線；待目標手機覆蓋率與穩定性驗證後再建立高畫質路徑 |

## 10. 無障礙、隱私與醫療內容治理

- 所有 3D 操作提供文字清單和鍵盤可操作入口。
- 支援螢幕閱讀器、足夠對比、大字體及減少動畫設定。
- 不因瀏覽或探索而收集病歷、診斷、療程等健康資料。
- 點燈與留言採最少資料原則；公開前須有明確同意及撤回方式。
- 病友故事須取得授權、去識別化並完成院內審查。
- 醫療內容須由對應專科審閱，標註版本與審閱日期，建立更新與下架流程。
- 不以單一成功個案暗示治療效果，也不以風險資訊造成責備或恐慌。

## 11. 驗收條件（初稿）

- 使用者可在手機和桌機完成全景、搜尋、清單及卡片閱讀。
- 每個上線據點都能從場景和文字清單到達，且連結至正確內容。
- 3D 載入失敗時仍能使用文字清單與衛教卡片。
- 所有核心流程可使用鍵盤操作；關鍵內容有文字替代。
- 醫療內容具有負責單位、審閱者或審閱流程及更新日期。
- 若啟用留言／點燈，公開同意、審核、撤下與資料刪除流程通過演練。
- 活動現場完成實際網路、裝置、投影與備援模式測試。

## 12. 建議開發階段與交付物

### Phase 1｜需求與內容盤點

- 確認活動受眾、活動形式、場地與上線時間。
- 確認院內單位、檢查室、流程和聯絡資訊。
- 建立衛教內容清單及醫療審閱責任表。

### Phase 2｜低擬真原型

- 2D 六角群島地圖、大螢幕鳥瞰版面與手機第一人稱畫面線框。
- 主要使用者流程、導覽路線、資訊卡範例。
- 先以一個六角區測試移動、點選、卡片閱讀與暈動感，再決定是否擴展完整 3D 群島。
- 院內團隊確認內容架構與導覽順序。

### Phase 3｜視覺設計與 3D 概念

- 台大癌醫 Q 版建築、六角區模組、島嶼全景與代表性據點模型。
- 卡片、標籤、色彩、圖示與動畫規格。
- 以低、中階手機測試第一人稱操控、模型複雜度與載入。

### Phase 4｜MVP 開發與內容上稿

- 完成六角 3D 全景、手機漫遊、搜尋清單、照護路線、卡片及備援模式。
- 加入活動頁、QR code 進場／據點深連結、主持人大螢幕模式與影音入口。

### Phase 5｜驗收與活動部署

- 醫療內容審閱、無障礙與跨裝置檢查。
- 活動場地測試、大螢幕模式及離線備援演練。
- 建立活動後內容保留、下架或轉為常設衛教的決策。
